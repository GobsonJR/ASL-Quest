# Database

ASL Quest uses SQLAlchemy as its ORM and Alembic for schema migrations. The
same codebase supports two database engines:

| Mode | Engine | When to use |
| --- | --- | --- |
| **Development (default)** | SQLite (`data/asl_quest.db`) | Local development, no setup required |
| **Production (recommended)** | PostgreSQL (`psycopg` v3 driver) | Deployed / shared environments |

Which one is used is controlled entirely by the `DATABASE_URL` environment
variable — nothing is hardcoded, and no application code changes between
modes.

## `DATABASE_URL`

Resolution order (see `backend/settings.py`):

1. `DATABASE_URL` environment variable, if set.
2. `ASL_QUEST_DATABASE_URL` (legacy name, kept for backward compatibility).
3. Local SQLite fallback: `sqlite:///data/asl_quest.db`.

Examples:

```bash
# PostgreSQL
DATABASE_URL="postgresql+psycopg://asl_quest:changeme@localhost:5432/asl_quest"

# SQLite (explicit; same as the default)
DATABASE_URL="sqlite:///data/asl_quest.db"
```

Never commit a real `DATABASE_URL` with credentials. Copy `.env.example` to
`.env` and fill in real values there (`.env` is gitignored).

## Schema management: Alembic

The database schema is defined once, in `backend/models.py` (SQLAlchemy ORM
models), and versioned as a linear chain of Alembic migrations under
`migrations/versions/`:

| Revision | Purpose |
| --- | --- |
| `0001_baseline` | Reproduces the schema that existed before the database-foundation work: `users`, `user_progress`, `letter_progress`, `challenge_progress`, `achievements`, `user_achievements`, `practice_sessions`, `xp_events`, `word_progress`, `word_practice_sessions`. |
| `0002_new_tables` | Adds the new, currently-unused-by-the-app tables: `words`, `native_signs`, `native_sign_references`, `native_sign_progress`, `native_sign_sessions`, `model_versions`, `sign_predictions`, `user_preferences`, `chatbot_conversations`, `chatbot_messages`, `chatbot_feedback`. |
| `0003_seed_words` | Data-only: populates `words` from the existing `backend/words/catalog.py` spelling catalog, keyed by the catalog's own string IDs (e.g. `"beginner-cat"`). Idempotent. |

**Nothing outside `backend/database.py`'s legacy `migrate_schema()` path
auto-creates tables anymore for the tables added in `0002`.** Application
startup (`init_db()`) still creates/updates only the original ten tables it
always has — new tables are created exclusively by running Alembic
migrations. This is intentional: it keeps "what created this table" always
traceable to a migration file.

### Common commands

Run from the project root, with `DATABASE_URL` (or `ASL_QUEST_DATABASE_URL`)
pointing at the target database (omit it to target the local SQLite dev db):

```bash
# Show the current revision of the target database
venv311\Scripts\python.exe -m alembic current

# Apply all pending migrations
venv311\Scripts\python.exe -m alembic upgrade head

# Roll back to a specific revision (e.g. undo the new Phase 2 tables)
venv311\Scripts\python.exe -m alembic downgrade 0001_baseline

# Roll back everything
venv311\Scripts\python.exe -m alembic downgrade base

# Show migration history
venv311\Scripts\python.exe -m alembic history

# Author a new migration after changing backend/models.py
venv311\Scripts\python.exe -m alembic revision --autogenerate -m "describe the change"
```

Always review an autogenerated migration file before running it — Alembic is
good at detecting structural changes but does not know your intent (e.g.
renames show up as a drop + add unless you edit the migration by hand).

### Fresh install (new SQLite file or new PostgreSQL database)

```bash
# 1. Create the target database (PostgreSQL only — SQLite file is created automatically)
createdb asl_quest

# 2. Point at it and run all migrations
DATABASE_URL="postgresql+psycopg://asl_quest:changeme@localhost:5432/asl_quest" \
    venv311\Scripts\python.exe -m alembic upgrade head
```

This creates all 21 tables and seeds the `words` catalog. The FastAPI app
does not need to run for this — migrations are independent of app startup.

## Local backup procedure

Before running any migration against a database that has real data (in
particular the local dev SQLite file, which is not otherwise version
controlled), make a timestamped copy:

```bash
mkdir -p data/backups
cp data/asl_quest.db "data/backups/asl_quest_$(date +%Y%m%d_%H%M%S).db"
```

Verify the backup opens and its row counts match the live file before
proceeding:

```bash
python -c "
import sqlite3
for path in ['data/asl_quest.db', 'data/backups/<your-backup-file>.db']:
    con = sqlite3.connect(path)
    cur = con.cursor()
    cur.execute(\"select name from sqlite_master where type='table'\")
    for (t,) in cur.fetchall():
        cur.execute(f'select count(*) from {t}')
        print(path, t, cur.fetchone()[0])
"
```

`data/backups/` is gitignored — it exists only as a local safety net, not a
backup strategy for production. For a real PostgreSQL deployment, use your
hosting provider's backup/snapshot tooling.

## Rolling back safely

If a migration causes a problem:

1. **Schema-only rollback:** `alembic downgrade <previous-revision>`. Every
   migration in this project has a matching `downgrade()`, and `0002`'s
   downgrade only drops the *new* Phase 2 tables — it never touches the
   original ten tables or their data.
2. **Full restore (SQLite dev only):** stop the backend, replace
   `data/asl_quest.db` with the most recent file from `data/backups/`, then
   run `alembic stamp <revision-matching-that-backup>` so Alembic's bookkeeping
   agrees with the restored file's actual schema.
3. **Full restore (PostgreSQL):** restore from your database provider's
   snapshot/backup, then `alembic stamp <matching-revision>`.

Never run `alembic downgrade base` or drop tables against a database with
real user data unless you have already confirmed a current backup exists and
is restorable.

## SQLite → PostgreSQL import

Once you're ready to move from local SQLite to a real PostgreSQL database,
use `scripts/migrate_sqlite_to_postgres.py`. It is **never run
automatically** — you run it by hand, once, when you're ready to cut over.

```bash
# 1. Create the Postgres database and bring its schema to head first
DATABASE_URL="postgresql+psycopg://asl_quest:changeme@localhost:5432/asl_quest" \
    venv311\Scripts\python.exe -m alembic upgrade head

# 2. Dry run — reports what would be copied, writes nothing
venv311\Scripts\python.exe scripts/migrate_sqlite_to_postgres.py \
    --source-url "sqlite:///data/asl_quest.db" \
    --target-url "postgresql+psycopg://asl_quest:changeme@localhost:5432/asl_quest" \
    --dry-run

# 3. Real run
venv311\Scripts\python.exe scripts/migrate_sqlite_to_postgres.py \
    --source-url "sqlite:///data/asl_quest.db" \
    --target-url "postgresql+psycopg://asl_quest:changeme@localhost:5432/asl_quest"
```

The script:

- Refuses to run if the target already has data in any table (`--force` to
  override — use with care).
- Refuses to run if the target's schema isn't already at Alembic `head`.
- Copies every table in foreign-key-safe order (computed from the ORM
  metadata, not hand-maintained), preserving primary keys exactly.
- Runs the entire copy in one transaction on the target — any error rolls
  back the whole import, never leaving it partially populated.
- Resets PostgreSQL's integer-PK sequences after a successful copy so new
  rows created by the app afterwards don't collide with imported IDs.
- Prints a before/after row-count report for every table.
- Never writes to the SQLite source database.

## Existing-table protections

- `backend/database.py::_LEGACY_TABLE_NAMES` lists the ten tables that
  existed before this database-foundation work. The app's own startup
  (`init_db()`) only ever creates/alters those — it will never implicitly
  create the newer tables even though they're registered on the same
  SQLAlchemy `Base`. Only `alembic upgrade` creates them.
- `WordProgress.word_id` / `WordPracticeSession.word_id` are untouched plain
  strings, exactly as before. The new `words` table reuses the same string
  catalog IDs (e.g. `"beginner-cat"`) from `backend/words/catalog.py` as its
  primary key, so existing progress rows resolve to the new table by simple
  ID equality — no migration of `word_progress`/`word_practice_sessions`
  data was needed or performed.
